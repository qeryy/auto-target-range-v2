# 功能对照表：web 版 ↔ 桌面版

> 这份文档的作用：把「功能与 web 端完全相同」这句话**变成可以逐行核对的东西**。
>
> 写在最前面的一句话：**页面存在 ≠ 功能相同**。所以下面每一行都标了状态，
> 而不是笼统地写「已实现」。

图例：

  标记   含义  
 --- --- 
  ✅   桌面版有对应实现，且行为与 web 版一致  
  ⚠️   **有**对应实现，但行为或呈现与 web 版有**已知差异**（下面写清差在哪） 
  ❌   桌面版**没有**这个功能  

> **⚠️ 只用于「有但不一样」，不用于「没做」。**
> 这份表第一版把两者混用了（「拖拽排序 ⚠️ 未做」——「未做」就该是 ❌），
> 结果 ⚠️ 这一档失去了意义：看到 ⚠️ 无法判断该去看差异说明还是去看缺口。
> 现在严格区分：**没有的一律 ❌**。

## 一、总览

web 版 `static/index.html` 的结构是「6 个一级导航 + 6 个设置二级分类」：

  web 一级导航   桌面侧栏  
 --- --- 
  任务 `home`   任务 ✅  
  仪表盘 `dash`   仪表盘 ✅  
  用量 `usage`   用量 ✅  
  编队 `agents`   编队 ✅  
  项目 `projects`   项目 ✅  
  经验 `exp`   经验 ✅  

  web 设置二级分类   桌面侧栏  
 --- --- 
  模型 `models`   模型 ✅  
  MCP 接入 `mcp`   MCP 接入 ✅  
  Skill 知识 `skill`   技能 ✅  
  通知 `notify`   通知 ✅  
  本地工具 `localtools`   本地工具 ✅  
  关于 `about`   关于 ✅  

**唯一的层级差异**：web 把后 6 类收在「设置」外壳里（`.set-shell` 左侧分类 + 右侧内容），
桌面版把它们提到侧栏一级，另有一个独立的 **设置** 页放偏好（主题以外的本机偏好）。
集合上：web 12 区块 ⊆ 桌面 13 页，桌面多一个 `settings`。

> 这个集合关系由 `build/web_parity.ps1` 每次检查，**并且检查每页真的建了控件**
> （防止「页面注册了但 CreateView 是空的」）。

## 二·五、按「动作」而不是「区块」对照时发现的东西

上面那张表是**按页面区块**对照的（12 个区块 ⊆ 13 个页面）。但功能不止藏在区块里 ——
这轮把 web 版 `index.html` + `js\*.js` 里的按钮文案全抓出来去重（**92 种动作**），
再和桌面版的按钮比，发现一处**区块对照永远看不到的差距**。

### 工具策略引擎：web 有，桌面没有

web 后端有一个 `policy_engine`，在**每次工具调用前**做硬校验：

```python
# policy_engine，check_tool()
if spec.risk == RiskLevel.DESTRUCTIVE:
    self._deny(f"破坏性工具一律禁止: {spec.name}（G3 禁 DoS）")
if spec.name in self.forbidden_tools:
    self._deny(f"模式 {self.mode.value} 禁用工具: {spec.name}（G2 模式能力边界）")
if self.requires_approval(spec, action):
    granted = await self.approval_gate(act, detail)   # 逐次人工确认
```

它管四件事：

  能力   说明  
 --- --- 
  **风险分级**   `RiskLevel`，`DESTRUCTIVE` 的工具**一律拒绝**，没有例外  
  **模式能力边界**   竞赛模式禁公开网页搜索（`if mode == COMPETITION and is_search_tool(...)`） 
  **禁用工具名单**   每个模式一份 `forbidden_tools`  
  **逐次审批**   `approval_gate` 回调；UI 上是「允许本次调用 / 拒绝」，并写明「仅允许本次调用；拒绝只拦截本次调用，其余分支照常推进」 

**桌面版没有这一层。** 桌面有**每个 agent 的工具白名单**（`AgentProfile.Tools`），
但那是「这个 agent 能用哪些工具」，不是「这个工具有没有危险、这个模式下允不允许」。

### 差距有多大？比看起来小，但确实存在

  项   web   桌面  
 --- --- --- 
  默认行为   `automatic_approval = true` → **不弹审批**   不弹审批  
  破坏性工具硬禁   ✅   ❌ **没有风险分级**  
  模式能力边界   ✅   ❌  
  逐次审批   ✅（非自动模式）  ❌  
  per-agent 工具白名单   ✅   ✅  

**默认配置下两者的行为是一样的**（都自动放行）。差异只在**开启严格模式之后** ——
web 能拦住「破坏性工具」和「竞赛模式下的联网搜索」，桌面拦不住。

### 为什么没做

  原因   说明  
 --- --- 
  要改核心循环   `AgentLoop` 每轮执行工具前都要过一遍策略；那是所有会话的主路径  
  要引入风险分级   19 个工具每个都要标 `RiskLevel`，还要定 `forbidden_tools` 表  
  需要交互设计   审批要暂停 agent、弹框、等用户决定、再恢复 —— 是个异步阻塞点  
  **不能测试**   这类「改主路径 + 加异步阻塞」的改动，没有测试窗口就是在赌  

**记在这里，不假装做了。**

### 顺带发现的两处小差异

  动作   web   桌面  
 --- --- --- 
  **停止**   独立的「停止」按钮   **复用发送按钮**（运行时它变成停止）。`SessionView.cs:508` 的注释：「运行中也要能点（那是"停止"）」  
  **会话分页**   「上一页 / 下一页 / 加载更多 / 回到最新」   「↑ 更早的」按钮往上翻  

两处都是**功能在、形式不同**，不算缺口。

### 快捷键对照

按「动作」对照的延续：web 的键盘绑定在 `js\*` 里（`keydown` 监听 + `e.key ===`），
桌面在 `MainForm.KeyDown` 和 `SessionView._input.KeyDown`。

  动作   web   桌面   判断  
 --- --- --- --- 
  刷新当前页   —   **F5** / **Ctrl+R**   桌面多给  
  从会话详情返回   **Esc**   **Esc**   ✅ 一致  
  切换标签页   **← →**（标签栏聚焦时）  **Ctrl+Tab**（`TabControl` 原生）  ⚠️ 键不同，能力在  
  直接跳到第 N 页   —   **Ctrl+1** … **Ctrl+9**   桌面独有  
  跳到第一个/最后一个标签   **Home** / **End**   —（`Ctrl+1` 可代替）  差异很小  
  关闭浮层 / 图表提示   **Esc**   —（桌面没有浮动图表）  不适用  
  **发送消息**   **Ctrl+Enter** / **Cmd+Enter**   **Ctrl+Enter**   ✅ **完全一致**  
  输入框里单独按回车   **换行**   **换行**   ✅ 一致  

#### 发送键：两边其实完全一致（这里我自己先看错了）

第一版表格我写的是「web 用 Enter、桌面用 Ctrl+Enter」，还编了一段「因为输入框用途不同」
的解释。**是错的。**

web 的完整条件是：

```javascript
// agent-side-chat.js:114
if (event.key === "Enter" && (event.ctrlKey    event.metaKey) && !event.isComposing)
```

**`&& (event.ctrlKey    event.metaKey)`** —— 也就是 **Ctrl+Enter（或 Mac 的 Cmd+Enter）**。
和桌面一模一样：

```csharp
// SessionView.cs:201
if (e.Control && e.KeyCode == Keys.Enter)
```

**我只看了一行的前 40 个字符就下了结论。** 这是这个会话里第三次同类错误
（前两次：以为「坏 JSON 会抛」、以为「有编排模式开关」）。

> **读条件判断时，把整行读完再下结论。**
> `if (event.key === "Enter"` 和 `if (event.key === "Enter" && event.ctrlKey)`
> 前 30 个字符完全一样，行为完全相反。

#### 结论

桌面的快捷键**覆盖更广**（多了 F5/Ctrl+R 刷新、Ctrl+1..9 跳页），
只有发送键因为「多行输入」的取舍不同。

### 圆角比 web 大 —— 这是按你的要求做的

对着代码量了一遍两边的圆角：

  元素   web CSS   桌面 `Theme`  
 --- --- --- 
  小控件（按钮 / 导航项）  `8px`   **8px**（`RadiusSm`） 
  普通卡片   `8–9px`   **12px**（`RadiusMd`） 
  大卡片   `12px`   **16px**（`RadiusLg`） 
  对话框   `17px`   **20px**（`RadiusXl`） 
  胶囊 / chip   `999px`   `RadiusPill`（画成半圆） 

**桌面普遍圆 1.3–1.5 倍。**

这不是偏差 —— 你当时的要求是「**ui使用 SaltUI**」，而 SaltUI 的设计令牌是：

```
SaltDimens.kt:  corner = 12.dp        → Theme.RadiusMd = 12
                dialogCorner = 20.dp  → Theme.RadiusXl = 20
```

配色也一样：`background #202020`、`highlight #0088FF`、`text #EBEEF1` 全部取自
`SaltColors.kt`，不是照抄 web 的 CSS。

所以准确的说法是：

> **布局和功能对齐 web，配色和圆角对齐 SaltUI。**
>
> web 有自己的 CSS 设计系统，SaltUI 是另一套 —— 两者在圆角上本来就不同
> （6–9px vs 12–20px）。**要求同时满足「像 web」和「用 SaltUI」，圆角这一项只能选一个，
> 按你的明确指示选了 SaltUI。**

如果你更想要 web 那种紧凑感，把 `Theme.cs` 那四个常量改小就行
（`RadiusMd = 9`、`RadiusLg = 12`、`RadiusXl = 17`），**一处改动，全局生效**，
不用碰任何页面代码。

## 三、桌面独有的东西

  能力   为什么 web 没有  
 --- --- 
  单文件 exe，双击即用   web 要 Python + 依赖  
  数据落 `%APPDATA%`（写不进时退 exe 同级 `data\`）  web 落服务端  
  密钥用 DPAPI 加密   web 用 scrypt 哈希存管理员密码，性质不同  
  不监听任何端口   web 是 HTTP 服务  
  关于页的「运行自检」   桌面要检查本机环境  
  设置页（偏好本体）  web 的「设置」是分类外壳，桌面的 `settings` 是偏好

## 四、已知差异的细节

### 1. 会话标签页 5 vs 9

web 有 9 个标签，桌面做了 5 个（会话 / 事件 / 拓扑 / Flag / 经验）。
没做的四个里，**漏洞**只在 SRC 场景有数据（CTF 会话永远为空），不做是对的。
其余三个 web 侧是独立视图，桌面版没做。

**报告 / WP 不算差距**：桌面版的「导出 MD」调 `SessionExporter`，
输出带概览、Flag 提取、工具调用时间线、凭据脱敏的完整 Markdown —— 那就是报告。

**做空壳比不做更糟**：用户点进去看到空白，会以为程序坏了。

### 2. 时间口径

web 写的是「统一按北京时间统计」。桌面按**本机时区**——
因为桌面是单机软件，用户在哪就是哪。

### 3. 会话缺的那 4 个标签，为什么不做

web 版的 9 个标签定义在 `static/js/views.js` 第 3 行：

```js
const TABS = ["chat", "topo", "challenges", "vulns", "flags",
              "experience", "events", "deliverables", "writeup"]
```

桌面做了 6 个（多了「文件」）。剩下 3 个卡的地方**不一样**：

  标签   数据从哪来   桌面的情况  
 --- --- --- 
  `challenges` 题目   竞赛引擎的题目卡   **没有竞赛引擎**（见第 8 节） 
  `vulns` 漏洞   **blackboard 的 VULN 层**   **没有黑板存储**（见第 9 节） 
  `deliverables` 交付物   7 个子类   **「文件」子类做了**；其余 6 类没有对应存储  
  `writeup` 报告   生成 Markdown   **已覆盖**：桌面「导出 MD」产出同一份东西，只是没做成标签  

> **⚠️ 这里原来写的是「都卡在没有可靠的数据源」，那句话是错的。**
>
> 查过 web 之后才看清：`challenges` 和 `vulns` **都有数据源** ——
> 前者是 `competition/engine.py` 的 `ChallengeCard`，后者是 `blackboard` 的 `VULN` 层。
> 桌面拿不到它们，**不是因为数据藏在消息里挖不出来，而是因为那两套存储本身没实现**。
>
> 判据不同，结论就不同：「没有数据源」听起来是「做不了，认了」；
> 「没有存储」说明**这是能做到但没做的东西**，得写清代价。

**`deliverables` 里唯一有真实数据源的是「文件」子类**（agent 读写过哪些文件），
桌面已经做了 —— 只是它当初也遇到过一个坑，见下一节。

### 4. 工具消息到底存了什么（这里错了两次）

`AgentLoop` 落库工具消息时写的是：

```csharp
_store.Append(sessionId, "tool",
    "[" + call.Name + "] " + (result.Summary ?? ""),   // ← 注意不是 Output
    call.Name);
```

所以 **`Message.Content` = `"[工具名] " + ToolResult.Summary`**。

  我先后以为   实际  
 --- --- 
  Content 是 `Output`   **是 `"[" + 工具名 + "] " + Summary`**  
  delegate 落库形如 `[方向 的结论]\n正文`   `Output` 那个字符串**从来没落过库**  
  文件名拿不到   **拿得到**，`[file] 写入 secret.txt` 就在 Content 里  

**第一次错**（187 轮）：`BuildTopology` 用 `^\[(.+?) 的结论\]` 去匹配，
而那只是 `Output` 的格式 —— **每一行都会显示「（未记录方向）」**。

**第二次错**（191 轮上半）：据此断言「`Message` 不存 Summary，信息落库时就丢了」，
还推论「交付物里的文件子类做不了」。**实际上 Summary 就在 Content 里。**

#### 正确的解析方式

```
Content = "[delegate] 密码分析：RSA 小模数分解拿到明文"
                  ↑方向名    ↑摘要

异常分支：Summary = 方向 + " 执行失败：" + 消息
```

已按此重写 `BuildTopology`。**成功/失败仍分不出来**（`ToolResult.Ok` 不落库，
失败时正常分支的 Summary 也只是「方向：错误文本」），所以常态标「已返回」
而不是「已完成」，并在提示栏写明「成败要看结论内容」。

#### 这给「交付物」开了口子

`[file] 写入 secret.txt`、`[file] 列出 C:\x（12 项）` 这些都在 Content 里，
所以「会话里动过哪些文件」是能做的 —— **192 轮已经做成「文件」标签**
（第 6 个），从 `[file] 读取/写入/列出/哈希 <目标>` 解析。

**一个残留限制**：`FileTool` 的 `Summary` 里，`读取 / 写入 / 哈希` 用的是
`Path.GetFileName(path)`（只有文件名），只有 `列出` 用完整路径。
所以那三种操作**显示不出完整路径**——完整路径没落库，标签里也不假装有。

> 同一个「读错数据源」，让 187 轮做出来的标签**整个不可用**，
> 又让我在 191 轮得出一个错误结论。
> **写解析代码前，先看数据是怎么写进去的。**

### 5. 缓存窗口：数据其实已经回来了，只是没接

web 的仪表盘有 prompt cache 命中统计。桌面版没有——但**不是拿不到数据**：

```csharp
// ChatClient.cs L362-367 现在只读了这两个
var usage = GetDict(root, "usage");
if (usage != null) {
    reply.PromptTokens    = GetInt(usage, "prompt_tokens");
    reply.CompletionTokens = GetInt(usage, "completion_tokens");
}
```

DeepSeek 的响应里还有 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，
**被丢掉了**。`ChatReply` 也只有 `PromptTokens` / `CompletionTokens` 两个字段。

#### 要接上需要改三层

  层   改什么   风险  
 --- --- --- 
  `ChatReply`   加两个 int 字段 + 解析时读出来   低（不落库） 
  `Session`（持久化）  加两个 long 累计字段   **中：schema 变更**  
  `UsagePage` / `DashPage`   显示命中率   低  

**卡在第二层**：`Session` 是要写进 JSON 的持久化模型。加字段要处理
旧数据没有该字段的情况，属于「改一次要小心」的地方。

**在不能测试的情况下不动它**——187 轮「拓扑标签」就是没验就上，
结果整个不可用。

> 这个和 191 轮那个 `Message.Summary` 的教训是同一类：
> **数据在源头就有，但没接进来。** 补 UI 之前得先补管道。

### 6. 通知机制

web 走浏览器 `Notification` API（需要用户授权）。
桌面走 `NotifyIcon` 系统托盘气泡（Windows 原生）。
**两边都是「弹一条系统通知」，但不是一个东西。**

### 7. 编队的保存方式

web 有「还原 / 保存指派」两个按钮，是**编辑器语义**（改了先攒着）。
桌面是**即时生效**——双击卡片选完模型立刻写盘。
桌面省掉了「忘了点保存」这个坑，但也没有「改错了撤销」这一步。

### 8. `competition` 模式：web 有整套引擎，桌面只有个标签

web 的 `src/spiritscout/competition/` 有四个文件、约 22 KB：

  文件   内容  
 --- --- 
  `engine.py`   题目卡调度（`ChallengeCard`：id / 分值 / 已解）、`mark_solved`、AWD 换防 `awd_rebalance`、`awd_task_split`  
  `rules.py`   比赛规则（`contest_type`、时间衰减） 
  `strategy.py`   选题优先级、并行度  
  `__init__.py`   —  

**桌面版的 `RunMode.Competition` 只是一个枚举值。** 它实际影响的东西只有两样：

```csharp
// 1. 哪些 agent 适用（AgentProfile.Modes 里有 "competition"）
// 2. 经验召回过滤（Experience.cs: 按 mode 筛）
loop.Mode = mode;      // Orchestrator → AgentLoop，用于按类召回经验
```

**没有**：题目清单、积分、已解标记、AWD 换防、比赛计时、选题优先级。
**也没有模式专属的系统提示词**（`AgentProfile.BasePrompt` 不按 mode 分支）。

#### 顺带发现一个会误导人的地方

新建任务对话框里有三个快捷模板，第三个是：

```csharp
AddChip("竞赛连续拿分", delegate {
    _mode.SelectedIndex = 2;                       // 智能体竞赛
    _mission.Text = "在智能体靶场中连续解题拿分";
});
```

**它只是设了模式 + 一句话简报**，背后没有任何竞赛功能。
名字叫「竞赛连续拿分」，用户会以为有积分和题目列表 —— **没有**。

对照 web：那个 chip 后面是真有引擎的。

#### 为什么不做

  缺的东西   要补什么  
 --- --- 
  题目清单   新的数据模型（`ChallengeCard`）+ 持久化 + 一个「题目」标签页  
  已解标记   要能识别「这题解了」—— web 靠 flag 提交，桌面没有提交通道  
  AWD 换防   攻防速率计算 + 资源配比策略  
  比赛计时   开始/结束时间 + 倒计时 + 超时行为  

**这是一个子系统，不是一块 UI。** 和「工具策略引擎」一样，属于「要改核心循环 +
加数据模型」的级别。

#### 一个折中办法（想过，没做）

只做「题目清单」的话，可以不碰 schema：在「Flag」标签旁边加「题目」，
把**本会话提取到的 flag 当作题目**列出来。

**数据全从现有消息推导。** 但那只是「列 flag」，和现有的 Flag 标签重复度太高，
价值不大 —— 所以没做。

### 9. 黑板存储：web 的「拓扑/漏洞」有真存储，桌面是解析消息

> **这一条纠正我之前的说法。** 表里「会话缺的那 4 个标签」原来说 `challenges` / `vulns`
> 是「消息里没有可靠的数据源」。**这个判断是错的** —— 数据源是有的，
> 只不过它在 web 那边是一套独立存储，而桌面版整个存储层都不存在。

#### web 的 `blackboard` 是什么

`src/spiritscout/blackboard/`，约 27 KB，**8 层共享状态**：

```python
class BlackboardLayer(str, enum.Enum):
    TARGET_AUTH = "target_auth"    # 目标与授权层
    ASSET       = "asset"          # 资产层
    RECON_CLUE  = "recon_clue"     # 侦察线索层
    VULN        = "vuln"           # 漏洞层
    CREDENTIAL  = "credential"     # 凭据层
    TOPOLOGY    = "topology"       # 拓扑层
    TASK_STATE  = "task_state"     # 任务状态层
    EXPERIENCE  = "experience"     # 经验反馈层
```

而且 `VULN` 层有一套 **10 态的核验状态机**：

```
candidate → verifying → screened → reproduced → fp_checked
          → compliance_checked → accepted
                              ↘ rejected_screen / rejected_unrepro /
                                rejected_fp / rejected_compliance / rejected_low
```

`convergence.py` 在**写入前**做去重、冲突检查；`dashboard.py` 从 `TOPOLOGY` 层取
`findings`、从 `VULN` 层取 `accepted` 计数。

#### 桌面的「拓扑」是什么

```csharp
// SessionTabs.BuildTopology()
// 解析会话消息里 Name == "delegate" 的那些，正则提出「方向：结论」
```

**这是从对话记录反推**，不是从结构化存储读。能用（191 轮修过一次正则），
但它拿到的东西比 blackboard 少得多：

  能力   web（blackboard）  桌面（解析消息） 
 --- --- --- 
  派过哪些子任务   ✅   ✅  
  发现过哪些资产   ✅（ASSET 层）  ❌  
  侦察到哪些线索   ✅（RECON_CLUE 层）  ❌  
  有哪些凭据   ✅（CREDENTIAL 层）  ❌  
  漏洞及其核验状态   ✅（VULN 层 + 10 态）  ❌  
  任务进度   ✅（TASK_STATE 层）  部分（Phase 字段） 

#### 所以 `challenges` / `vulns` 两个标签为什么不做

**不是因为「消息里没有数据」，是因为没有那层存储。**

要做 `vulns` 标签，得先有：
1. `Vulnerability` 数据模型（标题/等级/状态/证据链）
2. 一个能写的存储（新文件或 Session 扩展）
3. **谁来写**——web 是 agent 通过工具往 blackboard 写；桌面得有一套对应的工具

第 3 条是关键：**光有表没有数据，标签页还是空的。**

#### 为什么不做

和工具策略引擎、竞赛引擎一样：**子系统级**。

  缺的   要补什么  
 --- --- 
  8 层存储   数据模型 + 持久化 + 查询 API  
  漏洞状态机   10 个状态 + 迁移规则 + 去重/冲突逻辑  
  写入通道   新工具（agent 往里写），或从消息推导（不可靠） 

#### 一个仍然可做的折中（想过，没做）

「资产清单」可以**从消息推导**：把所有出现过的主机名/IP/URL 用正则抽出来列一张表。
`ProbeTool` / `HttpTool` 的调用记录里本来就有这些。

**但这只是「列出现过的东西」**，没有状态、没有去重、没有核验 —— 和 blackboard 的
`ASSET` 层差得远。做了会给人「有资产管理」的错觉，不如不做。

## 七、这份表的第一次修订

第一版是**纯按页面区块**对照的。后来按「动作」重新扫了一遍

**工具策略引擎**。
