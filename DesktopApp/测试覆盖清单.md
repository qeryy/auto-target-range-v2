### 3.5 并发写（第 61 轮）★ 最严重

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 8 线程 × 50 次写 config | **289 次异常** | **0** |
| 6 实例 × 30 次 Append | **161 次异常** | **0** |
| 最终消息数 | 180（侥幸） | **180（确定）** |
| 重复 / 丢失 | — | **0 / 0** |

异常类型：`文件正由另一进程使用`、`无法找到 .tmp`、**`集合已修改`**。

**根因**：`SessionStore._lock` 是**实例级**的，而各页面各自 `new SessionStore()`
——锁不共享。`JsonStore.Write` 那层一把锁都没有。

**用户怎么触发**：快速切换页面（每页刷新都可能写 config）。

**修复**：`JsonStore` 加静态 `WriteLock`；`SessionStore` 加静态 `WriteGate`，
`Save` / `Append` / `AddTokens` 都走它。`Append` 的「Load → 改 List → Save」
必须整体原子——光锁 `Save` 不够，会撞「集合已修改」。

**修复前「数据没丢」是侥幸**：失败写入没落盘，但内存缓存已被改过，
下次成功写入顺手带进去了。**进程中途退出就真丢了**。

**结果：10 / 10 = 100%**——每次查询的前 3 条命中全在同领域。

### 10.2 AgentLoop 整机链路（141 项，11-19 实测全通过）

前面的测试都是零件级。这条是**整机**：起一个假的 OpenAI 兼容服务，
第一次返回 `tool_calls`，第二次返回结论，跑真实的 `AgentLoop`：

```
模型说要调工具 → 工具真跑了 → 结果真回传 → 模型基于结果作答 → 会话真落盘
```

| 断言 | 结果 |
|---|---|
| SendAsync 成功 / 回复含预期 flag / token 统计 / 工具调用次数 | PASS ×4 |
| file 工具执行成功（`end:file:ok`）| PASS |
| 消息序列 `user → tool → assistant` | PASS ×2 |
| 假服务被调 2 次（工具轮 + 结论轮）| PASS |

### 10.7 卡片投影黑边（本轮，像素级取证）

「框旁边有黑边」这类问题在整页截图上看不出来，只有**沿卡边采样像素亮度**才说明问题。

| 采样点 | 修复前 | 修复后 |
|---|---|---|
| 氛围底色 | lum **23** | 23（没动）|
| 贴卡边最深 | lum **5**（#050608）| lum **18**（#0E1219）|
| 暗带宽度 | 8 px，外沿**一刀切断** | 5 px，渐隐回底色 |
| 卡面左缘 / 底缘 / 右缘 | 三条都有 | 三条都收口 |

两个真因都在 `Card` 这一层，且各自单独验过：

- **投影扩散 13px、画布只留 7px** → 超出控件边界被硬裁，留下最深那几环。
  改成环数 = 实际留白（`pad / 2`），四边对称外扩。
- **半透明投影环留在透明缓存画布上**，控件每重绘一次再合成一遍：
  单次叠加算出来 17%，实测 43%。改成渲染第一步铺祖先底色，卡面全不透明，
  重绘等于覆盖。

**用一次性探针把两种可能分开**（透明画布 vs 环叠加太深）：把同一套投影数学
搬到离屏位图上，先铺底色再 blit → 只暗 26%；真实界面暗 76% → 说明问题在
「画布不是不透明底」这一侧，不是公式本身。探针跑完即删。

回归面：13 页截图重拍 + `fit_check` / `clip_check` / `overflow_check` /
`color_check` 全绿；`ModeCard`（首页三张模式卡）的投影留白同步改成真实 pad。
